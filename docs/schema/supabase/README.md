## Why 02 and 03 are psql-only

1. **They are one transaction.** `BEGIN … SET LOCAL TIME ZONE 'Asia/Hong_Kong' … TRUNCATE … INSERT … checks … ROLLBACK`. Executed statement-by-statement with autocommit, the `TRUNCATE`s commit at once, a failed check leaves a half-load behind, the closing `ROLLBACK` undoes nothing, and the Hong Kong time zone is lost — every naive timestamp would shift by eight hours.
2. **Their results are `NOTICE` lines** (`B1 … OK`, `R6 … OK`, the counts). The editor discards them; you would learn only that nothing raised.
3. **`03` takes about two minutes** on the production dataset, most of it in the checks.
4. **Supabase's `pettycashv2` is the wrong source.** It holds the 23 test entities that are discarded at cutover. The production data reaches Supabase only as the *result* of a load done elsewhere — see `docs/modernisation/modernisation_plan.md`, Phase E: `rehearse.py` on a staging Postgres, then `pg_dump -n pettycash_test` → `pg_restore` into Supabase → one `ALTER SCHEMA … RENAME` transaction. The expected-skip numbers baked into the checks (98 reports, 22 sale_info rows, 239 restored contacts, 184 zero-count rows …) are measured on the production dataset; against any other data they fail on purpose and the transaction rolls back.

So the supported way to run them is

```
psql "$URL" -v ON_ERROR_STOP=1 -f docs/schema/supabase/02_data_foundation_rebased.sql
```

or, better, `python scripts/schema_migration/rehearse.py`, which runs the originals and flips
`ROLLBACK` to `COMMIT` for you.

## `pettycashv3` and the cutover

**Decided 2026-09-16: `pettycashv3` is the permanent schema name.** It is not swapped into
the `pettycashv2` name at cutover; the old schema stays `pettycashv2` for its retention period
and is then dropped. What follows from that:

- On the staging Postgres the loaders still fill `pettycash_test` (their target is baked in by
  `gen.py`), and the rehearsal ends with `ALTER SCHEMA pettycash_test RENAME TO pettycashv3` —
  `scripts/schema_migration/rehearse.py` does not do the rename itself. The first such build is
  the local database `minty_pettycashv3` (09-16 production dump, ALL GREEN).
- What reaches Supabase is `pg_dump -n pettycashv3 -Fc --no-owner --no-acl` of that result
  (`backups/minty_pettycashv3_20260916.dump`), restored with `pg_restore -d <supabase>
  --no-owner --no-acl <dump>` and **no `-n`** (that would strip the `CREATE SCHEMA`). It lands
  beside `pettycashv2`; nothing is renamed or dropped. Building this file on Supabase first is
  not needed — the dump brings the schema.
- Every schema qualifier in the three applications moves from `pettycashv2` to `pettycashv3`
  in Phase C (Minty `__table_args__` / `db.Enum(schema=)` / raw SQL / `SESSION_SQLALCHEMY_SCHEMA`
  / `tests/pg_harness.py`; billing-backend `db_table` and settings; onboarding
  `lib/refData.ts`). Until that lands, the applications keep running on `minty_cleanse`, where
  the new shape sits under the `pettycashv2` name.
