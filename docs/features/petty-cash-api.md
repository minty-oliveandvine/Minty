# Petty Cash API - what minty-petty-cash-web calls

Petty Cash is getting its own front end, `minty-petty-cash-web` (port 3010; its `docs/features/petty-cash-web.md`). That app reads and writes a company's petty cash through a **bearer JSON API**. Until 2026-10-14, every report, expense and settings route here was a session-cookie page or session AJAX (`report/routes/*`), with nothing a cross-origin app could call.

**Where it lives.** For now the API lives in this app as the blueprint `blueprints/petty_cash_api/`. The owner's target (2026-10-14) is a separate Django service, `minty-petty-cash-api`, on port 8010, serving **the same paths**. The front end reads it as `PETTY_CASH_API_URL`, so only that address changes when it moves. Flask's HTML pages and these routes call the same services. Each wave extracts a request-free service out of a route and points both at it, so there is no duplicated logic.

## The door (`guard.py`) - fails closed

Every rule is under `/api/petty-cash/v1/companies/<entity_id>`. The company comes from that address and nowhere else: not the body, and not the token's `entity_id` claim. A test checks that every rule starts with the prefix.

`before_request` runs these checks in order, before any view:

| Check | Refusal |
|---|---|
| `OPTIONS` | `204` with CORS, no token needed |
| A valid HS256 token carrying `module == MODULE_TOKEN_CLAIM`, minted by `_generate_module_token` (`bearer_api.claims_from_bearer`). An onboarding-scope token, a hub token without the claim, an expired token or a session cookie alone are all refused. | `401 {"error": "unauthorized"}` |
| The person exists and `approved` is true | `401` |
| Membership, or a superuser (`profile.entity_context`, the same test `/handoff/minty-web` uses). A stranger, an unknown id and a malformed id all get the same answer. | `403` "You don't have access to that company." |
| The company is past onboarding | `409` |
| Petty Cash is on (`modules._is_module_enabled`, which denies on every unknown) | `403` |

**Exceptions.** Anything that throws, in the guard or a view, goes to the blueprint's `errorhandler`. It rolls back, logs with `logger.exception` and answers `500` with "Something went wrong on our side. Please try again." The detail is never sent. Contrast `report.routes.module_guard`, the old pages' gate, which **lets a request through** when it cannot find the company or the check throws. That fail-open gate is still in place on the old pages; this surface does not inherit it.

**Responses.** Every response is JSON. A refusal is `{"error": "<sentence>"}`, a sentence the app shows as it stands. The one exception is `unauthorized`, which the app answers by going back through `/handoff/petty-cash-web`. Every response is `Cache-Control: no-store`.

**CORS** is stamped in `after_request`, so refusals and 500s carry it too:
- the origin is `PETTY_CASH_WEB_URL` (default `http://localhost:3010`), or a `petty-cash` preview-set origin where `PREVIEW_ORIGIN_REGEX` allows it;
- `Vary: Origin`;
- methods `GET, POST, PUT, PATCH, DELETE, OPTIONS`;
- headers `Authorization, Content-Type` only (no `X-Entity-Id`).

**CSRF.** The whole blueprint is exempt (`services/app_runtime/legacy/bootstrap.py`). That is safe only because nothing in the package reads the session cookie. `tests/test_petty_cash_api_door.py` parses the package and fails on a bare `session`, a `current_user` or a `login_required`.

## The way in: `GET /handoff/petty-cash-web?next=&entity_id=`

The hand-off is in `blueprints/entity/routes/modules.py`. Flask is the only minter, and the app has no refresh of its own: a lapsed token comes back here (the app's `lib/handoff.ts`).
- **Login-gated.**
- **`next` is a path only** (`safe_next`, never an open redirect). The default is the company's `/entity/<shortid>/<name>/petty-cash`.
- **`entity_id`** is a uuid **or the app's address form `<shortid>/<name>`**, resolved by `entity_ref.resolve`. The app's cookie lapses with its token, and after that its address is all it knows of the company.
- **Refusals:**
  - no company → minty-web's company list;
  - not a member → `entity.entity_list` with a flash, and no token;
  - onboarding → the wizard;
  - Petty Cash off → `entity.entity_list` with a flash.
- **Destination.** `<petty-cash-web>/landing?token=&entity_id=&entity_name=&next=`, through `preview_origin.handoff_origin("petty-cash", …)`, so a preview set stays in its set.

## Endpoints

| Method · path (under `/api/petty-cash/v1/companies/<id>`) | Answers |
|---|---|
| `GET ""` | `{company: {id, name, role, role_label, currency: {code, decimal_places} \| null}, person: {id, first_name, last_name, name, initials, email}}`: what the app shell needs before any page |
| `GET /home` | The dashboard's state. It comes from `entity/services/dashboard.py::dashboard_state`, the same function the Jinja dashboard reads. Fields: `server_today` (Hong Kong), `currency_code`, `latest` (the latest report, drafts included, and its deposit with whether it can be corrected), `draft` (the newest), `draft_date` (the earliest draft: the calendar's floor), `published` (submitted days, by date), `today_has_report`, `today_is_latest_report`, `xero_settings`, and `permissions` (`read_only` for a superuser outside the company, `correct_deposit`). The live Xero bank-account read the Jinja page makes is left out, because it feeds a control that page never shows. |
| `POST /deposit-correction` | `{kind: "change" \| "no", date, amount}`: the "Before You Start" correction of the previous day's deposit. Needs `REPORT_EDIT_ENTITY`, and bad input is refused with a 422. The work is `report/routes/legacy.py::correct_previous_deposit`, shared with the Jinja page's `/api/check-dept-bank-yest`. It may reverse or update the deposit in Xero. The answer adds `next_transaction_date` (the day to open next) in place of the Jinja page's Flask `redirect_url`. The body of the work is `routes/home.py::correct_deposit`, which `POST /api/internal/xero/deposit-correction` shares: the Django `minty-petty-cash-api` holds no Xero code, so it forwards this correction there (the owner's choice, 2026-10-15). |

| `GET /reports/opening?transaction_date=` | The Opening step (`REPORT_EDIT_OWN`). It is `report/services/opening.py::opening_state`, the same function the Jinja page renders from. Fields: the day, `currency_code`, the day's `draft` (status, section, completed sections, Xero and publishing state), `starting_cash_balance` (yesterday's closing, else the draft's own opening, else for a first report the onboarding balance), `yesterday_closing_balance`, `safebox_balance`, `cash_addition` and `withdrawal`. |
| `PUT /reports/opening` | `{transaction_date, cash_addition, withdrawal, action: "next"\|"exit"}`, then `save_opening`, shared with the Jinja page. **The opening balance is the server's:** "Starting Cash Balance", or a first report's onboarding balance; the Jinja page took it from a hidden form field. Refusals are 409 `{error, to}` with the Jinja page's own sentences: a date rule or a submitted day gives `to: "dashboard"`, a negative balance gives `to: "opening"`. Bad input is a 422. The answer is `{draft_id, transaction_date, current_section, completed_sections, next: "sales"\|"dashboard"}`. |
| `GET /reports/sales?transaction_date=` | The Sales step (`REPORT_EDIT_OWN`), from `report/services/sales.py`, the same service the Jinja page saves through. Fields: the day, `currency_code`, the day's `draft` (`null` before Opening made one), `methods` (the company's enabled electronic and delivery methods in Settings order: `sale_id`, `name`, `value_name`, `type`, and the day's `amount` or `null`) and `cash_sales`. Names are the catalogue's; the Jinja page title-cases them ("Wechat Pay"). |
| `PUT /reports/sales` | `{transaction_date, cash_sales, amounts: {value_name: amount}, action: "next"\|"exit"}`, then `save_sales`, shared with the Jinja page. A method left out is zero, as an emptied field is; an amount is 0 to 99,999,999,999.99, and a method the company has not switched on is a 422. No draft for the day gives 409 `{error, to: "opening"}`. The answer is `{draft_id, transaction_date, current_section, completed_sections, next: "expenses"\|"dashboard"}`. |
| `GET /reports/expenses?transaction_date=` | The Expenses step (`REPORT_EDIT_OWN`), from `report/services/expenses.py`, the service the Jinja page's routes share. Fields: the day, `currency_code`, `draft`, `lines` (`id`, `item` = the account's name, `amount`, `remarks`, `supplier {id, name}`, `account {id, code, name}`, `receipts [{id, name, mime_type}]`), `total`, `suppliers` (the company's SYNCED Xero contacts, A to Z - a line can only be saved with one of those), `accounts` (those switched on for Petty Cash) and `permissions.create_supplier`. No draft for the day is 409 `{error, to: "opening"}`, where the Jinja page redirects. |
| `POST /reports/expenses/lines` | Multipart `transaction_date, amount, remarks, supplier_id, account_id` and one `receipt`. **Checked here** (the Jinja routes leave every check to the browser): an amount above 0 and up to 99,999,999,999.99, a supplier and an account from the lists above, a description of at most 300 characters, one PDF / JPEG / PNG of at most 10 MB, judged by its bytes and stored as that type. 422 `{error}` otherwise; no draft is 409 `to: "opening"`. Answers 201 `{line, total}`. |
| `DELETE /expense-lines/<id>` | A line of this company's DRAFT (another company's or an unknown id is 404, a report no longer a draft 409). Asks what the Jinja route asks: `REPORT_DELETE_OWN` on your own report, else `REPORT_DELETE_ENTITY`. Answers `{total}`. |
| `GET /expense-lines/<id>/receipts/<attachment id>` | The receipt's bytes, inline, typed by its bytes, `nosniff` - by the attachment's id, never by its storage key. `can_view_report`. |
| `PUT /reports/expenses` | `{transaction_date, action: "next"\|"exit"}`. Next marks Expenses done and moves the report on to the deposit (committed by the service; the Jinja route relied on a later hook's commit); Exit records nothing, as Flask's page calls nothing. Answers `{draft_id, transaction_date, current_section, completed_sections, next: "deposit"\|"dashboard"}`. |
| `POST /suppliers` | `{name}` (1-150 characters, `CONTACT_CREATE`) -> a new contact in the company's Xero organisation, kept as a synced supplier (`entity/services/suppliers.py`, shared with `POST /entity/contact/create`). Answers 201 `{id, name}`; Xero's refusals are 409 with the Jinja route's sentences. |
| `GET /reports/deposit?transaction_date=` | The Bank Deposit step (`REPORT_EDIT_OWN`), from `report/services/cash.py`, the service the Jinja pages share. Fields: the day, `currency_code`, `draft`, and the figures - `opening_balance`, `cash_addition`, `cash_sales`, `expenses`, `bank_deposit`, `cash_on_hand` (before the deposit) and `expected_cash` (after it). No draft is 409 `to: "opening"`. |
| `PUT /reports/deposit` | `{transaction_date, bank_deposit, action}`. A deposit above the cash on hand is 422 `{error, field: "bank_deposit"}` naming the amount allowed (the owner's rule, 2026-10-15); a cash on hand already below zero is 409 `{error}`. Next marks Deposit done (`next: "cash_count"`); Exit keeps the report where it is (`next: "dashboard"`). |
| `GET /reports/cash-count?transaction_date=` | The Cash Count step: the same figures, the company's `denominations` (`id`, `value`, `kind` note/coin, the saved `count`) in its order, `safe_box_balance` and the saved `discrepancy {amount, kind, reason}` (amount negative = short). |
| `PUT /reports/cash-count` | `{transaction_date, counts: {<denomination id>: n}, safe_box_balance, discrepancy_reason, action, bank_deposit?}`. Counts are whole numbers of 0 or more; a denomination the company doesn't use is 422. The difference counts to the cent, and Save & Next with a difference and no reason is 422 `field: "discrepancy_reason"` (the owner's rules, 2026-10-15); Save & Exit keeps it without one. **With `bank_deposit`** the deposit is saved first and both in ONE transaction - Part 15's Cash Count stage, whose first section is the deposit; a refusal of either writes nothing. Answers the step's progress, `next: "ending"\|"dashboard"` and the stored `discrepancy {amount, kind}`. |
| `GET /reports/close?transaction_date=` | The last step (`REPORT_EDIT_OWN`): the draft's figures as Submit will post them - `opening_balance`, `cash_addition`, `sales {methods, cash, total, yesterday_total, history}` (`history`: the 30 days up to the day, `[{date, total}]`, one query; a report of any status counts, as on Flask's page), `expenses {lines [{id, item, supplier, remarks, amount, receipts}], total}`, `cash {bank_deposit, expected, counted, safe_box, difference {amount, kind, reason}}`, `closing_balance` (opening + addition + cash sales - expenses - deposit + the difference) - and `problem`, `{error, to}` naming what would stop the submit now, or null. No draft is 409 `to: "opening"`; a day already submitted is 409 `to: "submitted"` with its `report_id`. |
| `POST /reports/submit` | `{transaction_date}` -> `report/services/submit.py`, the Jinja Close page's submit too. Refusals are 409 `{error, to}` with the step that fixes it, and write nothing: a step not done, a future day, a drawer below zero, an expense line with no item or amount (`to: "expenses"`), **a difference that no longer matches the count** (a change after the count; the owner, 2026-10-15) or one with no reason (`to: "cash_count"`), a day already submitted (`to: "submitted"`, `report_id`). One commit under a row lock; a failure rolls back and never deletes the draft (Flask's clean-up did). Answers `{report_id, transaction_date, status, submitted_at, closing_balance, next: "submitted"}`. |
| `GET /reports/<report id>/outcome` | What the outcome page says (viewing rights; another company's or an unknown id is 404): `status`, `submitted_at`/`submitted_by`, `cash_counted` (drawer + safebox), `difference {amount, kind, has_reason}`, `xero {publishing_status, published_at, xero_integrated}`, `can_publish` (`REPORT_PUBLISH`), `is_today`, `next_day`, `company_name`. |
| `GET /reports/<report id>` | The Daily Report (viewing rights; another company's or an unknown id is 404 "Hmm, I couldn't find that report."): `status` with `status_label`/`status_tone` (the pill), `is_latest`, `submitted_at`/`submitted_by`, `published_at`, `publishing_status`, `xero_integrated`, `was_published` (it has been to Xero, even if edited since), `kpis {total_sales, total_expenses, cash_position}`, `sales {methods, cash, total, yesterday_total, history}` (a method switched off since still shows when it holds an amount; the last two as Close's), `expenses {lines, total}`, `cash {opening_balance, cash_addition, cash_addition_type, cash_sales, expenses, bank_deposit, expected, counted, safe_box, difference {amount, kind, reason}}`, `closing_balance`, and `permissions {edit, delete, publish, share, edit_details}` - edit (reopen) and delete only on the latest report; `edit_details` (the three edits below) on any submitted report not being published - with `options {suppliers, accounts}` (what a line may be changed to) only when `edit_details`. |
| `POST /reports/<report id>/reopen` | Back to a draft at Opening (`report/services/report_actions.py`, the Jinja Edit report too; `REPORT_EDIT_OWN`, the latest report only - 400 otherwise). A draft is 409 "This report is already a draft. Carry on with the Daily Closing."; a report Xero is publishing is 409. The Xero record is kept, so a resubmit reads Submitted and the page warns about duplicates. Answers `{report_id, transaction_date, status: "draft", next: "opening"}`. |
| `DELETE /reports/<report id>` | Deletes the latest report with its lines, sales, counts, Xero sync rows and receipts (the files only after the commit). A report in Xero **may** be deleted (the owner, 2026-10-15): the app warns first, from `was_published`, that its entries stay in Xero, a new publish adds a second copy, and Edit report is the way to change it. Refused: not the latest (400), Xero still publishing (409), no right (403). Answers `{deleted, transaction_date, next: "dashboard"}`. |
| `POST /reports/<report id>/share-link` | `{url}`: a read-only link to the day, valid 30 days, the same one renewed (`report/services/share.py`). A draft is 409 "A draft can't be shared. Submit the day first.". |
| `PUT /reports/<report id>/difference-reason` | `{reason}`: a submitted report's difference reason (`report/services/report_edits.py`, the Jinja Daily Report's too; `REPORT_EDIT_OWN`, any submitted report). 422 over 300 characters (Flask cut it) or empty when the cash was short or over. A draft ("Change it in the Daily Closing") or a report Xero is publishing is 409. The report leaves Xero (`mark_diverged_from_xero`). Answers the Daily Report. |
| `PUT /reports/<report id>/withdrawal` | `{withdrawal_type: personal|company}`: where the addition to the drawer came from; the amount stays. 400 for another word; the same 409s. Answers the Daily Report. |
| `PATCH /reports/<report id>/expense-lines/<line id>` | multipart `remarks`, `supplier_id`, `account_id` (send each only when it changes) and one `receipt`, replacing the line's receipts: never the amount. The supplier and account must be in `options` (422 "Choose a supplier / an account code from the list."); a new account renames the line (its item is its account's name); the receipt passes the Expenses step's checks; the replaced file leaves the bucket after the commit. A line of another report is 404. Answers the Daily Report. |
| `GET /reports?status=&start_date=&end_date=&page=&per_page=` | Report history (`report/services/history_query.py`, the Jinja page's list): one page, newest day first, `reports [{id, transaction_date, status, status_label, status_tone, current_section (where a draft resumes), total_sales, total_expenses, submitted_by (first name), created_at (when the day was started), submitted_at, published_at, was_published (as the Daily Report's, for the delete warning), publish_reasons [{text, resolved}] (a failed publish only), permissions {edit, delete}}]` - edit and delete only on the latest report, never a draft - with `page`, `per_page`, `total_pages`, `total_count`, `latest_report_id`, `currency_code` and `can_publish`. Filters as the page's chips (`draft`, `submitted`, `published`, `failed`), both dates or neither, 10/25/50/100 a page. Where the page falls back on a bad filter this refuses it, 422 with the sentence: an unknown status, a page below 1 or not a number, another page size, one date alone, a date not `YYYY-MM-DD`, a start after the end. minty-petty-cash-api builds the same list itself and asks `POST /api/internal/xero/publish-reasons` (`history_query.publish_reasons_for`, the same reasons) for the failed rows on its page (the owner's choice, 2026-10-16). |
| `GET /settings` | Petty Cash settings without Xero (`COA_VIEW`, as Flask's page; a cashier reads it): `country {country_code, currency_id, countries [{code, name}], currencies [{id, name}], selected_country, selected_currency}`, `sales_methods {electronic, delivery}` (switched-on methods in list order, `[{id, name, value_name, shared}]` - `shared`: another company has it too, so a rename is refused; Cash is the report's, never listed), `available {electronic, delivery}` (catalogue methods not on the list), `xero_connected`, and `permissions {edit_country, view_sales_methods, add_sales_method, rename_sales_method, remove_sales_method, reorder_sales_methods}`. The Xero mapping and the account codes stay on Flask's page (the owner, 2026-10-16): they read Xero live and can write to it. |
| `PUT /settings/country` | `{country_code, currency_id}` -> `apply_country_currency_selection`, as the page's Country & currency Save (the four rights that Save needs: `ENTITY_UPDATE` and `COA_UPDATE/CREATE/DELETE`). A country alone brings its currency; an explicit currency wins; the denominations follow it. Checked by `country_currency.checked_country_currency`, shared with minty-web's Entities & Integration save: an unknown country or currency is 422 (Flask's page skips it silently), and neither is 422. Answers the settings read plus `message`. |
| `POST /sales-methods` | `{type: electronic|delivery, sale_info_id}` (a catalogue method from `available`) or `{type, name}` (a new one, 1-100 characters; it joins the shared catalogue, as on Flask's page). 422: another type (`other` is Cash's), an empty or too-long name, an id not offered for that type; 409 a name already on the list (any case). 201 with the settings read. |
| `PUT /sales-methods/order` | `{type, method_ids}`: one type's full list in its new order (the other type keeps its own). A list that isn't exactly the type's current one is 409 (it changed since it was loaded). |
| `PUT /sales-methods/<id>` | `{name}`: renames the method. It renames the catalogue row, so a method another company uses is 409 (add a new one instead), as the service rules. |
| `DELETE /sales-methods/<id>` | Switches the method off for this company; reports that used it keep their amounts, and it is offered again in `available`. An id that isn't one of this company's Electronic or Delivery methods (Cash included) is 404. |

The app is ported from Flask's pages one at a time (`development` of minty-petty-cash-web): dashboard, then the report wizard, history, settings and Xero publish. Each new route needs a row here, an entry in `tests/_baseline/route_inventory.json` and its tests.
